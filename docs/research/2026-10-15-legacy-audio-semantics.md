## Role muting and line boundaries

- `TwoSkulls.ino` attaches `onSpeakingStateChange` to the animator; the callback calls `audioPlayer->setMuted(!isSpeaking)`. The code comment states why: both skulls play the same synchronized audio, but each should speak only its assigned lines. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:149) and callback registration at [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:349).
- A role's script lines are filtered at skit start: primary keeps speaker `A`, secondary keeps speaker `B`; then speaking is true only while `playbackTime >= timestamp && playbackTime < timestamp + duration - SKIT_AUDIO_LINE_OFFSET`. The offset constant is **0 ms**. Thus the interval is start-inclusive/end-exclusive, with no end clipping/tail pad. See [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:96), [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:112), [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:133), and [skull_audio_animator.h](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.h:109).
- Each A2DP request consumes PCM from the common queue. If `m_muted` is set, the player zeroes the returned `Frame[]` before invoking the frame callback. The animator then analyzes those frames, so the silent role sees zero RMS and closes its jaw. Playback still advances on both peers while muted, preserving the same script timeline. See [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:56), [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:96), [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:104), and [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:109).
- An inter-line gap has no matching speaking line, so `setSpeakingState(false)` is called and the role mutes; a continuous same-role pair separated by a gap mutes during that gap. Checked-in `.txt` files all have 3 comma-separated fields and valid nonnegative integer timestamps/durations; there is no fourth jaw field in the current sample set. I inspected 11 script files. All adjacent intervals touch exactly except `Skit - milkshakes.txt`: line 7 (B, 11520 ms, 2000 ms) ends at 13520 ms, and line 8 (B, 15000 ms, 1760 ms) starts at 15000 ms, leaving a 1480 ms all-role silence. See [milkshakes script](</Users/cam/Documents/Projects/TwoSkulls/sd_card_files/audio/Skit - milkshakes.txt:6>).
- `m_currentSkitLineNumber` is updated when a matching interval is found but is not reset when the interval ends. Speaking state still toggles off correctly; line-number logging can retain the previous line during gaps. At each new audio path it resets to `-1`.

## RMS jaw and eye behavior

- Current animator computes RMS over both signed 16-bit channels from the frames supplied for each A2DP callback. It applies amplitude smoothing factor **0.1**, gain **5.0**, clamps at **15000**, thresholds adjusted amplitude below **1000** to zero, maps `[0,15000]` linearly to configured servo `[min,max]`, then applies jaw-position smoothing factor **0.2** against the prior position. No FFT is actually executed in this code despite `arduinoFFT` include, buffers, and constructor setup. See [skull_audio_animator.h](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.h:13), [skull_audio_animator.h](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.h:66), [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:176), and [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:223).
- No frames means jaw goes to the configured minimum and resets smoothing. The animator calls `interruptMovement()` on every update before setting position. During skit role silence, frames are zeroed by the player, so RMS maps to the closed/min position through the threshold. This is the real audio-driven jaw behavior to preserve; there is no manual jaw-position playback in the active path.
- Parsed `ParsedSkitLine::jawPosition` exists and the parser accepts an optional fourth column (`toFloat`, otherwise sentinel `-1`), but a whole-repository reference search found no read of `line.jawPosition` in the animator or other runtime. Therefore it is metadata-only/unused today; do not accidentally imply that scripts currently drive exact jaw angles. All 11 supplied scripts omit the field. See [parsed_skit.h](/Users/cam/Documents/Projects/TwoSkulls/parsed_skit.h:6), [sd_card_manager.cpp](/Users/cam/Documents/Projects/TwoSkulls/sd_card_manager.cpp:90), and [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:198).
- Eyes are `BRIGHTNESS_MAX` while the local role is speaking and `BRIGHTNESS_DIM` otherwise (100/255). Max is driven by direct HIGH; dim uses PWM. This reflects role intervals, including gaps, rather than the audio file's global active state. See [skull_audio_animator.cpp](/Users/cam/Documents/Projects/TwoSkulls/skull_audio_animator.cpp:163), [light_controller.h](/Users/cam/Documents/Projects/TwoSkulls/light_controller.h:16), and [light_controller.cpp](/Users/cam/Documents/Projects/TwoSkulls/light_controller.cpp:33).
- Other servo behavior worth preserving separately from the audio jaw loop: idle breathing is scheduled every 7 seconds, with a 30-degree opening and 2-second open/close moves. `smoothMove()` blocks in 20 ms steps and the helper adds a 100 ms pause. Keep this out of the radio/audio callback in the port; run motion from a control task/state machine. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:81), [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:182), and [servo_controller.cpp](/Users/cam/Documents/Projects/TwoSkulls/servo_controller.cpp:114).

## Script syntax and parser behavior

- Script pairing: for each `/audio/Skit*.wav`, startup finds a similarly named `.txt` and parses it into lines. A line is intended as `speaker,timestamp_ms,duration_ms[,jaw_position]`; supplied examples use only `A|B,start_ms,duration_ms`. Nonblank lines are trimmed; the parser reads first char as speaker and uses the first three commas to parse fields. See [sd_card_manager.cpp](/Users/cam/Documents/Projects/TwoSkulls/sd_card_manager.cpp:35), [sd_card_manager.cpp](/Users/cam/Documents/Projects/TwoSkulls/sd_card_manager.cpp:73), and [README.md](/Users/cam/Documents/Projects/TwoSkulls/README.md:75).
- Current parser is permissive and unchecked: it does not validate speaker, integer conversion, field count, nonnegative values, positive duration, interval order, overlap, or file duration. `String::toInt()` is assigned to unsigned `unsigned long` fields, so a negative parsed number can wrap to a very large unsigned time/duration; malformed missing-comma indices can produce nonsensical `substring` ranges or zero conversions. A fourth-column invalid float becomes Arduino's float conversion result and no explicit error is raised. `lineNumber` counts accepted nonblank lines, not physical source line numbers. See [sd_card_manager.cpp](/Users/cam/Documents/Projects/TwoSkulls/sd_card_manager.cpp:84) and [parsed_skit.h](/Users/cam/Documents/Projects/TwoSkulls/parsed_skit.h:6).
- Inspection of all checked-in `.txt` files found no negative/malformed lines or optional jaw fields. This describes repository assets only; it does not validate private SD-card content. Milkshakes is the one observed timing gap; no overlaps were found by comparing adjacent end/start times.

## Selection, cooldown, and startup / Marco–Polo sequence

- Selector starts each skit at `playCount=0,lastPlayedTime=0`. Before a selection it sorts descending by `weight = log(now - lastPlayedTime + 1) / (playCount + 1)`. It takes at most the first three in that sorted order, excluding the immediately previous skit, then chooses uniformly among that pool. The selector increments the chosen skit's play count and timestamp immediately. If the skit list is empty, the code falls through to `selectedIndex=0` and indexes an empty vector; the caller should refuse triggers when parsing yields no playable skits. See [skit_selector.cpp](/Users/cam/Documents/Projects/TwoSkulls/skit_selector.cpp:16), [skit_selector.cpp](/Users/cam/Documents/Projects/TwoSkulls/skit_selector.cpp:48), and [skit_selector.cpp](/Users/cam/Documents/Projects/TwoSkulls/skit_selector.cpp:99).
- On file playback end, `TwoSkulls.ino` also calls `updateSkitPlayCount(filePath)`, which increments count and refreshes timestamp again for that exact path. Therefore a successfully selected skit is counted twice (once at selection and again at end). The no-repeat rule still applies based on last selected/updated name. Preserve no-repeat intent; decide explicitly whether reproducing the double weighting bug is desirable. Also note the selector's first three after a sort are chosen uniformly, not proportionally to weights. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:319) and [skit_selector.cpp](/Users/cam/Documents/Projects/TwoSkulls/skit_selector.cpp:85).
- Trigger acceptance is primary-only and requires peer BLE connection, A2DP speaker connection, no active audio, and `millis()-lastTimeAudioPlayed > 10000`. A successful remote BLE characteristic update is read back and compared before the primary queues local playback. `lastTimeAudioPlayed` is refreshed during active playback and on end, so the practical 10-second cooldown begins at/after the end. Failed/invalid trigger attempts are consumed/reset without retrying the same interrupt. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:457).
- Startup queues role-specific `Initialized - Primary.wav` or `Initialized - Secondary.wav` after A2DP setup. BLE initialization is delayed until the initialization-file end callback sets `isDonePlayingInitializationAudio`; the main loop then starts BLE exactly once. This provides the startup ordering: establish A2DP/audio path and play init clip first, then begin peer BLE. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:275), [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:319), and [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:450).
- While primary is in BLE `SCANNING`, it checks every 5 seconds and queues `/audio/Marco.wav` only when A2DP is connected and no audio is active. The timer is reset whenever it leaves scanning. Secondary's BLE connection callback queues `/audio/Polo.wav` if A2DP is connected and not playing. These are normal queued clips, so Marco/Polo can be suppressed by the active-player gate; preserve the “only after init, Marco while scanning, Polo after peer connects” ordering. See [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:118), [TwoSkulls.ino](/Users/cam/Documents/Projects/TwoSkulls/TwoSkulls.ino:428), and [README.md](/Users/cam/Documents/Projects/TwoSkulls/README.md:10).

## Audio data path and bounded native-port recommendation

- Existing `AudioPlayer` has an 8 KiB PCM circular buffer and declares 44.1 kHz, 16-bit, 2-channel audio (~46 ms of audio). It queues paths, reads SD in 512-byte chunks, and places absolute byte positions for file start/end markers. But `provideAudioFrames()` takes a `std::mutex`, and when the ring is empty it calls `fillBuffer()` from inside the A2DP data callback. `fillBuffer()` reads SD, opens/closes files, and can recurse through bad paths; this is unbounded callback work and should not be ported as-is. See [audio_player.h](/Users/cam/Documents/Projects/TwoSkulls/audio_player.h:49), [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:57), [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:145), and [audio_player.cpp](/Users/cam/Documents/Projects/TwoSkulls/audio_player.cpp:218).
- Audio is pulled/consumed by A2DP, while script role state, RMS jaw, and eyes currently execute synchronously from the frame callback. A native port should separate these into bounded responsibilities: (1) a deterministic boot-time script validator/parser producing immutable schedules, (2) an SD producer task streaming PCM into a bounded ring, (3) an A2DP callback that only copies available aligned frames, zero-fills shortage/EOF, advances a monotonic frame index, and returns the required frame count, and (4) a control/animation task consuming compact timestamped frame/RMS/role events and issuing servo/light updates. Keep the direct BLE path and send the same asset ID/path to both peers; both consume the same unmuted timeline, with role-specific zeroing applied at the exact frame interval so muted-side jaw RMS remains zero as today.
- Deterministic RIFF/WAVE parsing should replace the hard-coded `seek(128)`: verify `RIFF`/`WAVE`, walk bounded chunks with little-endian sizes and even-byte padding, locate `fmt ` and `data` regardless of order/extra chunks, validate PCM encoding and the expected sample rate/channel count/bits, reject truncated/overflowing chunks, and start at the actual data payload. Stream only complete stereo frames and track data byte length; zero-fill at end instead of reading header/junk bytes. Do not assume the header is 44 or 128 bytes. This is a recommendation for the later pipeline, not validation of current card WAV variants.
- To preserve exact role semantics with low scheduling jitter, convert each interval boundary to the first sample frame for which the old floored playback millisecond reaches that boundary (for 44.1 kHz, boundary frame `ceil(ms*44100/1000)`), use `[startFrame,endFrame)`, keep the offset at 0 unless owner-approved script changes set another value, and mute only the frame output based on that role interval. Count the actual PCM frames consumed, not wall-clock task wakeups. Treat any future fourth-column jaw control as an explicit new feature until product intent is agreed, because it is currently parsed but ignored.
- Existing PCM callback order has a subtle boundary consideration: it calls the audio-frame callback before applying file-start/end marker callbacks at the bottom of `provideAudioFrames()`. A replacement should publish path/asset identity and frame position consistently with the bytes returned, especially when the ring spans a file boundary.
